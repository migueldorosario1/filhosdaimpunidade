# Lição: worktree compartilhado — commit de outro agente pode VARRER seu conteúdo resolvido (ronda 232ª)

**Data:** 2026-09-06 ~09:06-09:10 · **O quê:** durante o `git pull --rebase` da ronda 232ª, o rebase conflitou em de_dell.md (o DS-Dell 225ª anexou ao mesmo fim de arquivo, ~1 min antes). Resolvi o conflito (mantive os 2 blocos em ordem cronológica), `git add` + `git rebase --continue` → "Successfully rebased". Mas um agente concorrente (Revisores, rodando no MESMO worktree, fora do meu sandbox) commitou com `add -A`-like logo depois: o commit dele (f11bdbf0c → virou 7bc84eb8c no push) carregou JUNTO os meus 5 arquivos resolvidos (de_dell com meu bloco DS-N-232, CONTEXTO_MINI 09:00, memoria 232º, seed da obra 09:05, canal DSN-F 363-366). Sintomas: meu commit 316a3844d sumiu do main (não é ancestral), o topo do log era um commit "DSN Revisores" que NÃO era meu, e o `git status` oscilava entre staged/limpo sem explicação; o stash do arquivo do vizinho conflitou no pop (UU) porque o commit dele já continha aquilo.

**Por quê:** agentes da casa rodam no mesmo clone/worktree em paralelo (eu no sandbox do harness, os outros em processos próprios no servidor). Durante um rebase meu (HEAD destacado + índice com meus arquivos staged), outro agente que rode `git commit -a`/`git add -A` varre TUDO que está staged/worktree — inclusive minha resolução de conflito — e o commit dele vira o dono do meu conteúdo. O `git rebase --continue` depois concluiu sobre uma base que já não tinha meu commit, e o conteúdo foi parar no commit do vizinho.

**Como aplicar:**
1. **Integridade de CONTEÚDO, não de hash**: depois de qualquer turbulência de git (rebase/merge/push negado), conferir se meus marcadores existem em `origin/main` (`git show origin/main:<arquivo> | grep <marcador>`) — não procurar meu hash de commit (rebase reescreve; add -A do vizinho engole).
2. **Não deixar estado staged/rebase aberto por muito tempo**: resolver conflito e concluir rebase/push no mesmo fôlego; quanto mais tempo com HEAD destacado + índice staged, maior a janela de varredura por agente concorrente.
3. **Conferir `git log --oneline -3` + `git status` ANTES do push** e, se o topo não for meu commit, verificar se o conteúdo está no commit do topo (árvore) — se estiver, seguir (push entrega o conteúdo); se não, refazer o commit.
4. **Stash do arquivo alheio pode conflitar no pop** quando o dono commitou/pushou no meio — nesse caso o stash é redundante (conteúdo já commitado): resolver com `git checkout HEAD -- <arquivo>` + `git stash drop`, nunca forçar merge de versão velha.
5. **Nunca usar `git add -A`/`commit -a` em worktree compartilhado** — regra da casa mantida (add seletivo); o incidente mostra o risco quando OUTRO agente viola: minha defesa é a verificação de conteúdo no origin pós-push (método das lições 110ª/165ª, agora estendido a conteúdo embarcado em commit alheio).
